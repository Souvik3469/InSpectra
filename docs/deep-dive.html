InSpectra — Deep Dive A floating DevTools panel: run JS in the real page context, inspect network traffic, keep snippets

Scope The README covers what InSpectra does, feature by feature. This document covers how — the constraints Chrome's extension model imposes, and the choices made to work inside them. It also says where the implementation is weak.

0. Overview

Four execution contexts, and why

The whole architecture follows from one platform constraint: a Chrome extension's content script runs in an "isolated world" — its own JavaScript realm, sharing the DOM with the page but not its globals. It cannot see window.myAppState, cannot call page functions, and cannot patch window.fetch in a way the page will observe.

InSpectra needs both isolation (so a React UI doesn't collide with the page) and page access (so user code can touch page globals, and so fetch can be intercepted). So it runs in four places:

Nothing shares memory across those boundaries. Every interaction is a message — the full protocol is in message-protocol.md.

1. Code Execution

The CSP problem — the decision that shaped the project

To run user code with access to page globals, that code must be evaluated in the page's realm. The obvious way is to append a <script> element:

const s = document.createElement('script')
s.textContent = userCode
document.documentElement.appendChild(s)   // ← blocked by CSP

This is what InSpectra originally did, and it fails on any page with a strict Content-Security-Policy — which is most local dev servers and most hardened production apps. Precisely the pages a developer tool needs to work on.

The fix chrome.scripting.executeScript({ target: { tabId }, world: 'MAIN', func, args }). Chrome injects this at the engine level, and it is not subject to the page's CSP. Same access, no CSP dependency.

The cost is a real constraint: the injected function is serialised across a process boundary, so it must be entirely self-contained — no imports, no closure references, no TypeScript helpers. That is why pageExecutor is one large ES5-flavoured function with its own serialisers inlined rather than composed from modules. It looks unidiomatic next to the rest of the codebase, and it has to.

REPL persistence — the trick and its cost

A browser console remembers your variables between commands. Reproducing that is harder than it looks, because let and const are block-scoped: declare one inside an eval and it's gone the moment evaluation ends. var at global scope attaches to window and survives.

var replCode = code.replace(/\b(let|const)\b/g, 'var')
...
var result = (0, eval)(evalCode)   // indirect eval → runs in GLOBAL scope, not local

(0, eval) rather than a bare eval is deliberate — bare eval inherits the calling scope; the comma expression turns it into an ordinary function reference, which forces global-scope evaluation. That detail is the difference between variables persisting and not.

Tracking which variables belong to the REPL is done by diffing window: snapshot Object.keys(window) before evaluation, diff after, accumulate the new names into window.__qcReplVars. That array backs both the N vars badge and the clear-state button.

Where this breaks The rewrite is a blind regex over the entire source, so it also rewrites let and const inside strings, template literals, comments, and property names. console.log("const x") prints var x. { const: 1 } becomes a syntax error. The code comment calls it "best-effort, ~95% of real usage", which is honest — but it corrupts input silently rather than failing loudly. A real tokenizer is the fix, and would remove the whole class of bug.

Top-level await, and why it needs a second trick

await is only legal inside an async function, so code containing it is wrapped in an async IIFE. But that reintroduces the original problem: var inside a function is function-scoped, so declarations stop reaching window.

// detected: /\bawait\b/
var lifted = []                       // extract simple `var name` declarations
var preDecls = 'var a; var b;\n'      // pre-declare them at global scope
var innerCode = replCode.replace(/\bvar\s+([\w$]+)\b/g, '$1')   // strip `var` inside
evalCode = preDecls + '(async function(){\n' + innerCode + '\n})()'

Declare the names globally first, then strip var inside the IIFE so the assignments target those globals. Awaited code persists its variables like everything else.

Documented limitation: comma-separated (var a = 1, b = 2) and destructured (var {x} = o) declarations aren't lifted, so they don't persist. And the lifting regex shares the string-blindness of the first one.

Console capture, and one subtle ordering choice

Before evaluation, the four console methods are swapped for capturing versions that record the value and forward to the original. Afterwards they're restored — but in finish(), not in a finally block.

Why that matters A finally would restore the console the instant eval returns. If the snippet returned a Promise, every console.log emitted while it settled would be missed — which is most of the interesting output from any await fetch(...). Restoring inside finish() means capture stays live until the work is actually done.

The tradeoff: while the console is swapped, logging the page itself does is captured too, and appears as though it came from the user's snippet.

2. Serialisation — twice, on purpose

Every value crossing postMessage must be structured-cloneable. Functions, DOM nodes, class instances and circular structures are not. So pageExecutor converts each value twice:

serialize()toTree()
Producesa flat stringa tagged node graph
Feedsthe console output linethe expandable object inspector

Element cap20100 array / 50 object
Cyclesdepth cap onlypath-tracked via seen

toTree tags every node (prim, str, arr, obj, err, cut) and carries a collapsed preview ((3) [1, 2, 3], {name: "Alice", …}) so the UI can render depth without re-walking anything.

Cycle detection is path-based: push on entry, pop on exit, so a repeated sibling is still rendered while a genuine cycle is cut. Correct — but it linear-scans an array per node, which is quadratic on wide graphs. The two depth caps also disagree, so the flat line and the tree beside it can truncate at different points.

3. Network Interception

network-interceptor.js is injected at document_start in the MAIN world — early enough to replace window.fetch and window.XMLHttpRequest before page code captures references to them. A window.__isNetActive guard prevents double-wrapping when SPA navigation re-injects.

fetch is wrapped as a function; XHR is replaced by a subclass overriding open, setRequestHeader, and send, with listeners on load, error, abort, and timeout.

The buffer — the part worth stealing

const _buf = []
let _ready = false
function post(data) { _ready ? window.postMessage(data, _origin) : _buf.push(data) }

window.addEventListener('message', (e) => {
  if (e.data?.type === IS_NET_READY && !_ready) {
    _ready = true
    _buf.splice(0).forEach((d) => window.postMessage(d, _origin))
  }
})

Requests fire during page load — long before a React panel can mount. Without buffering the Network tab would be empty for exactly the requests a developer most wants to see. Events queue until the content script announces itself with IS_NET_READY, then drain in order and stream live thereafter.

Unbounded _buf has no cap. On a page where the panel is never opened, IS_NET_READY never arrives and the buffer grows for the page's lifetime. The interceptor also runs on every page regardless of whether InSpectra is ever used there, and clones every response body to read it — work paid on every site the user visits.

Initiator recovery

There's no API for "which line fired this request", so the interceptor throws an Error at call time, walks the stack for the first frame that isn't chrome-extension://, and reduces it to filename:line. Cheap, and it reproduces the most useful column in the DevTools Network panel.

4. Panel & State

React 18 + Zustand, mounted into an injected root in the isolated world. The store persists to chrome.storage.local through a custom adapter wrapping Zustand's createJSONStorage — chrome.storage is callback-based and async, so it needs promisifying before the middleware can use it.

Persisted: panel position and size, active tab, editor contents, snippets, execution history. Ring-buffered: outputs at 200, network requests at 500.

Drag and resize are hand-rolled hooks (useDraggable, useResizable) rather than a library — for an extension injected into arbitrary pages, that avoids shipping a dependency into every site the user visits.

5. Build

A custom build.js rather than plain Vite config, because MV3 wants several independently-bundled entry points — service worker, content script, MAIN-world interceptor — each with different output shapes, plus manifest and icon handling. npm run dev watches.

6. What I'd Do Differently

  1. Parse instead of regex-replace. The let/const rewrite is the core of REPL persistence and it operates on text. A tokenizer that understands strings, templates and comments would eliminate an entire class of silent corruption. This is the single highest-value change available.
  2. Gate the network interceptor on activation. Patching fetch and cloning every response body on every page the user visits is a real cost paid by people who never open the panel there. Cap _buf while I'm at it.
  3. Honour isRecording at the source. The toggle currently filters the UI; the interception work happens regardless.
  4. Rename the page-context globals. window.__qcReplVars is left over from when this was QuickConsole. They're visible in the page's global scope, in a tool whose entire purpose is inspecting page globals.
  5. Reconcile the two depth caps — 3 and 5 for the same value is a bug waiting to confuse someone.
  6. Test the transform. There are no tests. The let/const rewrite is a pure function with well-understood edge cases — a dozen unit tests would have caught the string-literal problem before it shipped.
Calibration The weaknesses here cluster in one place: source transformation by regex. Nearly everything else — the CSP diagnosis, the MAIN-world split, origin-scoped postMessage, console restoration timing, the network buffer, path-based cycle detection — was reasoned about carefully and documented in the code at the time. That is a meaningfully different failure profile from "didn't think about it".
