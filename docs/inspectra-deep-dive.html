InSpectra — Deep Dive

InSpectra was named QuickConsole until commit 8f342aa. Same codebase. Some page-side globals still use the old __qc prefix.

1. Overview

What it is. A Chrome Manifest V3 (MV3) extension that puts a floating, draggable panel on any http(s) page. The panel has three tabs:

  • Console — a CodeMirror editor. Code runs in the page's own JavaScript realm, so it can read page globals. Declared variables persist between runs, the way DevTools' console behaves.
  • Network — a live list of every fetch and XMLHttpRequest the page makes, with headers, bodies, initiator (file:line), cURL, and JSON or HAR export.
  • Snippets — saved code, with rename, search, JSON import and export.

Stack.

Scope. No backend, no accounts, no network calls of its own. Everything runs inside the browser. There are no automated tests.

Key term — "world". A Chrome content script runs in an isolated world: it shares the page's DOM but has its own JavaScript globals. The MAIN world is the page's own realm, where window.fetch and page variables live. InSpectra needs both, which drives the whole design.

New to browser extensions? Section 1.1 below defines every term this document uses — world, service worker, CSP, indirect eval, structured clone, monkey-patching and the rest — in plain language before any of them are relied on. Nothing later assumes knowledge that is not introduced there.

1.1 The concepts, in plain English

This project leans on browser-extension and JavaScript-runtime ideas that do not come up in ordinary web app work. Everything the rest of the document assumes is defined here first. Skim it once; the later sections repeat the short version wherever a term is actually used.

Browser extension. A small bundle of HTML, CSS and JavaScript that Chrome loads alongside normal web pages and grants extra powers to — reading tabs, injecting code, storing data outside any one site. Manifest V3 (MV3) is the current rulebook for how those bundles are written. manifest.json is the bundle's declaration form: which files exist, when each one runs, and which powers it is asking for.

Service worker (the "background" script). The extension's own always-reachable-but-not-always-running process. It has no UI and no page attached to it. Chrome starts it when an event it subscribed to happens (here: the toolbar icon is clicked, or a content script sends it a message) and may kill it again seconds later when idle. So it can hold no long-lived state in memory. Think of it as a desk clerk who is fetched when the bell rings and wanders off afterwards.

Content script. Extension JavaScript that Chrome injects into a web page. It can see and change that page's DOM — the live tree of HTML elements the browser renders — so it is how an extension draws UI on top of someone else's site. InSpectra's React panel is a content script.

Isolated world vs MAIN world — the single most important idea here. Chrome runs a content script in an isolated world: it shares the page's DOM, but it gets its own private copy of the JavaScript environment. If the page sets window.currentUser = {...}, the content script's window.currentUser is undefined. They are two separate JavaScript universes pointed at the same document. The page's own universe is called the MAIN world — that is where the page's variables live, and where window.fetch is the function the page actually calls.

Why it matters: a developer console is useless if it cannot see the page's variables, and a network logger is useless if it cannot see the page's real fetch. Both of those live in the MAIN world. But React, the extension's storage and the message APIs are easiest to use from the isolated world. So InSpectra has to live in both worlds at once and pass messages between them. That constraint explains nearly every design decision in this document.

chrome.scripting.executeScript. The extension API that asks Chrome itself to drop a function into a page, and crucially, lets you pick which world it lands in. InSpectra uses { world: 'MAIN' } to run user code in the page's own universe.

Content Security Policy (CSP). A header a site can send that tells the browser "refuse to run any JavaScript except from these sources." It is an anti-XSS defence, and most modern apps and dev servers ship one. The naive way to run code in a page — creating a <script> element and appending it — gets blocked by CSP. Code injected by chrome.scripting, however, is injected by the browser rather than by the page, so CSP does not apply to it. That is issue F1 in section 7.1.

window.postMessage. A browser-level mailbox. One script posts a plain-data message onto a window; anything listening on that window's message event receives it. It is the only channel the isolated world and the MAIN world both reach, since they share the DOM window object but no variables. The second argument is the target origin — the https://host:port the message is allowed to be delivered to. Passing '*' means "any origin may read this", which is how issue F3 leaked results to cross-origin iframes.

Structured clone. The copying rule postMessage uses. It can carry numbers, strings, arrays, plain objects, Map, Date and so on, but it throws on anything with behaviour attached — functions, DOM elements, class instances with methods. So a result cannot simply be posted; it must first be turned into plain data. That conversion is serialisation, and section 4.6 is about it.

REPL. Read–Eval–Print Loop: the interactive prompt in a console where each line you type is evaluated immediately and its value shown. The defining behaviour is that state carries over — type const x = 5, then on the next line type x and get 5. Making that work across separate injected executions is the hardest part of InSpectra's console.

var vs let / const, and why the rewrite exists. A top-level var declared in global scope becomes a property of window, so it is still there the next time anything runs. A top-level let or const does not — it lives in a hidden declarative scope that disappears with the script. To make variables persist between runs, InSpectra text-replaces let/const with var before evaluating. That trick works, and it also has sharp edges, because var and let differ in more than storage: let creates a fresh binding each loop iteration, var creates one shared variable. Dry run 6.3 shows exactly that biting.

eval and indirect eval (0, eval). eval(code) runs a string as JavaScript. Called normally it runs in the caller's local scope, so a var inside it would land in that local function, not on window. Writing (0, eval)(code) instead — a comma expression that evaluates to the same function but detaches it from the eval name — triggers what the spec calls an indirect eval, which is specified to run in global scope. That is the mechanism that puts the user's variables on window where the next run can find them.

IIFE (Immediately Invoked Function Expression). (function(){ ... })() — a function defined and called in one breath, used to get a private scope or, with async, to get a place where await is legal. Also a bundle format: an "IIFE build" is a JavaScript file that is one self-contained block with no import statements, which is what Chrome requires for content scripts.

Promise, async / await, thenable. A Promise is an object standing in for a value that is not ready yet; it eventually settles (resolves with a value, or rejects with an error). await p pauses the surrounding async function until p settles. Top-level await means writing await outside any function — legal in a module, not legal in the kind of code eval runs, which is why InSpectra wraps such code in an async IIFE. A thenable is any object with a callable .then method; checking for one is how code asks "is this value asynchronous?" without caring whether it is a real Promise.

fetch and XMLHttpRequest (XHR). The two ways a page makes HTTP requests from JavaScript. fetch is the modern Promise-based one; XHR is the older callback/event-based one, still used by many libraries (axios, for one). A network logger has to cover both.

Monkey-patching (wrapping). Replacing a built-in function with your own version that records something and then calls the original. window.fetch = myVersion means every later fetch(...) in that page goes through myVersion first. It is how InSpectra sees requests at all, and why the interceptor must be careful to return exactly what the original returned — the page must not be able to tell the difference.

document_start vs document_idle. When Chrome injects a script into the page: document_start is before the page's own HTML is even parsed; document_idle is after the page has finished loading. The interceptor must run at document_start to wrap fetch before the page's first call; the React panel runs at document_idle because it needs a DOM to mount into. The gap between the two is why the interceptor buffers events — nobody is listening yet.

Zustand store, persist, partialize. A store is one object holding the app's shared state plus the functions that change it; React components subscribe to it and re-render when the slice they read changes. Zustand is a small library for that. Its persist middleware (a wrapper that adds behaviour around the store) automatically saves the state to storage and reloads it on start. partialize is the filter that picks which keys get saved.

chrome.storage.local vs sessionStorage. chrome.storage.local belongs to the extension: one shared bucket across every tab and every site, surviving browser restarts. sessionStorage belongs to the page — scoped to one tab and one origin, wiped when the tab closes, and readable by the page's own scripts. InSpectra deliberately splits state across the two: preferences and snippets are yours everywhere, captured requests belong to the tab you captured them in.

Ring buffer. A list with a fixed maximum length that drops the oldest entry when a new one arrives. Used here so an open panel on a chatty page cannot grow until the tab runs out of memory.

CodeMirror, extensions, keymap. CodeMirror is the embeddable code editor component — syntax highlighting, selection, autocomplete. Its behaviour is assembled from extensions, small plugin objects passed in as an array. A keymap is one such extension that binds keys to actions; InSpectra uses one to make ArrowUp walk back through previous commands.

Tagged union, and type guards. A tagged union (or discriminated union) is a value that could be one of several shapes, where one agreed field says which shape it is. TreeNode in section 4.1 uses the field k: k: 'str' means the string fields are present, k: 'arr' means the array fields are. The compiler can then check that code handles each case. A type guard is a small function like isNetworkEvent(data) that inspects an unknown value at runtime and tells TypeScript "it really is this type" — the correct way to handle data arriving from outside the program, such as over postMessage (issue F4).

Shadow DOM and CSS specificity. Injecting UI into an arbitrary page means the page's CSS can wreck it and vice versa. Shadow DOM is the browser's built-in fix: a subtree whose styles are sealed off from the document. InSpectra does not use it; it instead relies on specificity — the ranking CSS uses to decide which rule wins when two apply. An id selector like #inspectra-root outranks most ordinary selectors, so prefixing every panel rule with it usually wins. all: initial is the blunt companion: reset every property on the panel root so nothing inherits down from the page.

HAR and cURL. Two standard ways to hand a captured request to another tool. cURL is a shell command line (curl -X POST 'https://…' -H '…') you can paste into a terminal to replay the request. HAR (HTTP Archive) is a JSON format that Chrome DevTools, Postman and Charles all import, so a HAR export drops straight into whatever the next person uses.

Blob and object URL. A browser cannot write a file to disk directly. The workaround: wrap the content in a Blob (an in-memory file-like object), call URL.createObjectURL to get a temporary blob: URL pointing at it, create an invisible <a download> targeting that URL, click it in code, then revoke the URL. That is the whole of triggerDownload.

Stack trace as an initiator. new Error().stack gives the chain of function calls that led to this line, with file names and line numbers. No extension API reports which line of page code started a request, so the interceptor throws away a fake error purely to read its stack, skips the frames belonging to the extension itself, and reports the first page frame as the request's initiator.

React terms used below. A hook is a function starting with use that lets a component hold state or run side effects; useEffect runs code after render (and can return a cleanup function); useMemo caches a computed value so it is not rebuilt on every render (issue F5 was a missing one). A re-render is React re-running a component to produce new output — cheap individually, expensive when it happens on every one of 500 network events. An error boundary is a component that catches a crash in its children and shows a fallback instead of leaving a blank overlay (issue F6). beforeunload is the browser event fired just before a page navigates away — the last chance to save anything.

2. HLD

2.1 Components

The shape of it. Four pieces of code, living in three different places, cooperating by passing messages. The service worker is the extension's dispatcher: it wakes on a toolbar click and it is the only one allowed to inject code into a page. The content script is the visible product — the React panel — but it sits in the isolated world, so it can see the page's HTML and nothing of the page's JavaScript. The network interceptor and pageExecutor are the two pieces that do live inside the page's own JavaScript universe: one permanently (swapping out fetch), one for a single run (evaluating your code). Nothing here is a server; it is four scripts in one browser tab talking over mailboxes.

2.2 Data stores

Four places, because they answer different questions. chrome.storage.local is the extension's own drawer — your snippets and where you like the panel, the same on every site and after a restart. sessionStorage belongs to one tab on one site and is wiped when you close it — the right home for "the requests I just captured here". The Zustand store is plain memory, the live copy everything renders from, gone on reload. And window.__qcReplVars is a page global, because it has to be: it is the list of variables your console created, and those variables live on the page's window, so the bookkeeping has to live next to them.

2.3 Communication

Why four different transports for what is basically one app. Each pair of components can only reach each other one way, and the API is dictated by which boundary is being crossed. Extension-to-tab uses chrome.tabs.sendMessage; tab-to-extension uses chrome.runtime.sendMessage (needed because a content script is not trusted with chrome.scripting itself, so it has to ask the service worker to inject on its behalf). Crossing the isolated/MAIN world boundary cannot use any chrome.* API at all, because the MAIN world is just the page and has no extension privileges — the only thing both sides share is the DOM window, so they shout across it with postMessage.

2.5 Deployment topology

There is nothing to deploy. No server, no account, no hosting — "deployment" here means the folder Chrome loads. npm run build produces dist/, and you point chrome://extensions at it in developer mode. The notable line below is host_permissions on all http and https URLs: that is the broadest permission an extension can ask for, and it is required because the tool is meant to work on any page you open. It is also the hardest thing to justify in a Web Store review.

  • npm run build writes dist/ (manifest, three bundles, CSS, icons). The user loads dist/ as an unpacked extension.
  • public/manifest.json declares permissions: storage, activeTab, scripting and host_permissions on all http and https URLs.
  • Both content scripts match http://*/* and https://*/*. Neither sets all_frames, so iframes are not instrumented.
  • npm run dev runs the same three builds in watch mode, unminified, with source maps.

3.2 Flow A — toggle the panel

  1. chrome.action.onClicked in src/background/index.ts — gets the active tab id, sends { type: MSG_TOGGLE }. Errors are swallowed for pages with no content script.
  2. chrome.runtime.onMessage handler in src/content/App.tsx — matches MSG_TOGGLE, calls toggle().
  3. toggle in src/content/store/index.ts — flips isVisible.
  4. Panel in src/content/components/Panel.tsx — re-renders; returns null when hidden.

3.3 Flow B — run code

  1. ConsoleTab.tsx — Run button or Ctrl/Cmd+Enter calls run(resetIndex).
  2. hooks/useCodeExecution.ts — guards against double runs, adds to history, sets isExecuting.
  3. utils/executor.ts — executeCode mints an id, arms a 10 s timeout, registers a window listener, sends MSG_EXECUTE.
  4. background/index.ts (listener) — reads sender.tab.id, calls chrome.scripting.executeScript in MAIN.
  5. background/index.ts (pageExecutor, now inside the page) — rewrites code, evaluates, captures console, posts MSG_RESULT.
  6. utils/executor.ts — listener matches the id, clears the timeout, resolves the promise.
  7. hooks/useCodeExecution.ts — applyResult adds outputs, return value or error, and updates replVarCount.
  8. store/index.ts → ConsoleTab.tsx → OutputLine.tsx / ObjectTree.tsx — render.

3.4 Flow C — capture a network request

  1. network-interceptor/index.ts — at document_start, wraps window.fetch and XMLHttpRequest.
  2. Same file, isFetch or ISXHR.send — posts a req event, then a res or err event, through post.
  3. Same file, post — queues into _buf until ready, else window.postMessage.
  4. content/App.tsx — on mount, posts IS_NET_READY; the interceptor flushes _buf in order.
  5. hooks/useNetworkMessages.ts — validates with isNetworkEvent, drops events if isRecording is false, calls addNetworkRequest or updateNetworkRequest.
  6. components/NetworkTab.tsx → network/DetailView.tsx → network/BodyBlock.tsx — list, detail, body view.

3.5 Flow D — export requests

  1. NetworkTab.tsx — checked rows are held in local checkedIds state.
  2. exportSelectedJson or exportSelectedHar — filters networkRequests by checkedIds.
  3. utils/reportGenerator.ts — downloadReport → reportToJson → buildReport, or downloadHar → harToJson → buildHar.
  4. triggerDownload — creates a Blob, an object URL and a temporary <a download>, clicks it, revokes the URL.

4.2 Store (usePanelStore)

One object, four concerns. Everything the UI shows lives in a single Zustand store, split into four groups: the panel frame (where it is, how big, which tab), the console, the snippets, and the network list. Components subscribe to the parts they read and re-render when those change. The interesting design is not the state itself but what gets saved where — covered right below.

Persistence split — the rule is does this belong to you, or to this tab?

  • partialize sends only position, size, isRecording, editorCode, snippets, activeTab to chrome.storage.local. These are user preferences and saved work, shared across all sites.
  • isVisible and networkRequests are per-tab, saved by App.tsx into sessionStorage on beforeunload. So a reload restores the open panel and recent requests for that tab only.
  • execHistory and outputs are not persisted.
  • chromeStorage wraps chrome.storage.local in Promises, because Zustand's createJSONStorage expects a Promise-returning getItem.

4.4 Message protocol

Why a protocol at all. Nothing here can call a function in another component — they are in different processes or different JavaScript worlds — so every interaction is a message with a string type and a payload, like a tiny API. The __IS_… strings are deliberately odd-looking because window.postMessage is a shared channel: the page and any library in it also post messages on that same window, so the type string is what distinguishes InSpectra's traffic from everything else. The executionId serves the same purpose in time rather than space — two runs can overlap, so each result carries the id of the run that produced it and the listener ignores anything else.

All type strings live in src/shared/constants.ts.

4.6 Serialisation (inside pageExecutor)

Values cross postMessage by structured clone, which rejects functions and DOM nodes. So each value is converted twice.

Why twice. The panel shows each result in two forms at once: a one-line summary you read at a glance, and an expandable tree you click into. Building both in the page, in a single walk of the value, means the panel never has to touch the original object — which it could not do anyway, since the original never left the page. serialize produces the line, toTree produces the tree. The caps exist because an object graph can be enormous or circular, and the only defence when walking an unknown value is to refuse to go past a fixed depth and a fixed number of children.

serialize(v, depth)toTree(v, depth, seen)
Outputflat stringTreeNode
FeedsConsoleOutput.valuesConsoleOutput.tree, returnTree
Depth cap3 (returns [...])5 (returns cut)
Element cap20 array items / 20 keys100 items / 50 keys
Cyclesstopped only by depth capseen is the current ancestor path; push on enter, pop on exit
Previewn/afirst 3 items via shortVal, e.g. (3) [1, 2, 3]

The cycle problem. const a = {}; a.self = a — walking that naively recurses forever. The fix is seen: the list of objects on the path from the root down to where the walker currently is. Before descending into an object, check whether it is already on that path; if it is, this is a loop, so emit cut and stop. On the way back out, pop it off again — which is why an object that merely appears twice side by side is drawn twice rather than cut.

Because seen holds only ancestors and depth stops at 5, the linear scan over seen costs at most 5 comparisons per node. A value repeated in two sibling branches is rendered twice; only a true cycle is cut.

4.7 CSS isolation

The problem being solved. The panel renders inside somebody else's page, so that page's CSS applies to it. A site with button { font-size: 3rem } or div { display: flex } would visibly deform the panel, and the usual culprit, inherited properties like font-family and color, flows down into it from <html>. Shadow DOM would seal this off completely; InSpectra skips it (partly so the React tree and Tailwind stay straightforward) and wins the fight on points instead — reset everything at the root, then make every panel rule outrank the page's by hanging it off an id selector.

  • The panel is not in a Shadow DOM. It is a plain div#inspectra-root appended to <html> (not <body>, so it survives body replacement by SPAs).
  • tailwind.config.js sets important: "#inspectra-root", so every utility is prefixed with the root id, which raises its specificity above most page rules. preflight is off, so Tailwind's global reset is not shipped into the page.
  • panel.css applies all: initial on the root to cut inherited page styles, then a zero-specificity :where(#inspectra-root *) base.

5. LLD — function-wise flow

5.1 Run code

The trick, before the twelve steps. Your code has to run in the page's universe, must be able to use await, and its variables must still exist on the next run. Those three pull against each other, and steps 6 to 10 below are the compromise: textually swap let/const for var so the variables land on window; if the code contains await, hoist those variable names out and wrap the rest in an async function so await is legal while the assignments still hit the globals; evaluate the result with indirect eval so it all happens in global scope. Meanwhile console.log and friends are temporarily replaced with versions that record what they are given before forwarding it to the real ones, which is how output reaches the panel. Everything is put back in finish. It works, and most of what it gets wrong comes down to one thing: a regular expression is not a good enough stand-in for a JavaScript parser.

  1. run(onRun?) in hooks/useCodeExecution.ts. Input: editorCode from the store. Returns early if isExecuting or the code is blank. Calls addToHistory(editorCode), then onRun (which is resetIndex, resetting the history cursor), sets isExecuting = true. Awaits executeCode. On reject, adds an eval-error output with the message. Always clears isExecuting in finally.
  2. executeCode(code) in utils/executor.ts. Builds id = EXEC_PREFIX + Date.now() + '_' + counter++. Starts a 10 s setTimeout that removes the listener and rejects with Execution timed out after 10 seconds. Adds onMessage on window, which accepts only type === MSG_RESULT && id === id. Sends { type: MSG_EXECUTE, code, executionId: id }. In the response callback: if chrome.runtime.lastError it does nothing (the timeout handles it); if response.error it clears the timer and rejects.
  3. chrome.runtime.onMessage listener in background/index.ts. Ignores other types. Without sender.tab.id it responds { error: 'No tab ID — cannot inject script' }. Otherwise calls chrome.scripting.executeScript({ target: { tabId }, world: 'MAIN', func: pageExecutor, args: [code, executionId, MSG_RESULT] }). Responds {} on success or { error: 'Cannot script this page: ...' } on failure. Returns true to keep the response channel open.
  4. pageExecutor(code, execId, msgType) in background/index.ts, now running in the page. It must be self-contained: Chrome serialises the function source, so it cannot use imports or closures. Steps 5 to 10 happen inside it.
  5. Console hook — saves bound originals of console.log/warn/error/info in orig and replaces them with makeCapture(type). Each capture pushes { type, values: serialize(...), tree: toTree(...) } to captured, then forwards to the original.
  6. Rewrite — replCode = code.replace(/\b(let|const)\b/g, 'var'). A top-level var evaluated by global eval becomes a property of window, so it survives to the next run.
  7. Snapshot — _before = new Set(Object.keys(window) + existing __qcReplVars).
  8. Async wrap — if /\bawait\b/ matches: collects names with /\bvar\s+([\w$]+)/g, emits var a; var b; pre-declarations, strips var inside, and wraps the body in (async function(){ ... })(). This keeps await legal while assignments still target globals.
  9. Evaluate — result = (0, eval)(evalCode). The comma expression makes this an indirect eval, which always runs in global scope instead of the caller's scope.
  10. Settle — if result has a callable then, attaches .then / .catch handlers that call finish, and returns; console capture stays active until then. Otherwise calls finish(serialize(result, 0), toTree(result, 0, []), undefined). A thrown error goes to finish(undefined, undefined, { message, stack }).
  11. finish(rv, rvTree, err) inside pageExecutor. Restores the four console methods. Computes new window keys not in _before (skipping __qc* names) and appends them to window.__qcReplVars. Posts { type: msgType, id: execId, result: { outputs, returnValue, returnTree, error, replVars } } to window.location.origin, or '*' only when the origin is the string 'null' (e.g. file://). Restoration is in finish, not in a finally block, so logs emitted while a returned Promise settles are still captured.
  12. applyResult(result) in hooks/useCodeExecution.ts. Adds one output per captured console call. Then adds either an eval-error (message plus stack) or a return output, skipping a return value of 'undefined'. Sets replVarCount = replVars.length.

5.2 Clear REPL state

Why this needs a button at all. Because variables persist by being parked on window, they keep accumulating until the page reloads — and one of them might shadow something the page itself needs. "Clear vars" runs a tiny script in the page that deletes each name InSpectra remembers creating. Step 3 is the subtle part: a normal top-level var cannot be deleted, but a variable created by eval can, because the spec marks the ones eval makes as configurable. The feature works only because of how the variables were created in the first place.

  1. clearRepl() in useCodeExecution.ts — skips if executing; sets isExecuting; calls clearReplState.
  2. clearReplState() in executor.ts — builds an IIFE that runs delete window[k] for each name in window.__qcReplVars, then sets it to []. Sends it through executeCode.
  3. The delete works because bindings created by eval are configurable, unlike var in a normal <script>.
  4. applyResult sets replVarCount to 0 from the returned empty replVars.

5.3 Network capture

In one paragraph. Before the page runs a single line of its own, the interceptor replaces window.fetch and window.XMLHttpRequest with wrappers. Each wrapper records what is being sent, calls the real one, records what came back, and returns exactly what the real one returned — the page cannot tell it has been instrumented, and an error has to be re-thrown rather than swallowed or the page's own error handling would break. Each request produces up to three messages: req when it starts, then either res or err. Since this all begins before the panel exists, the early messages pile up in _buf and are flushed in order the moment the panel announces itself with IS_NET_READY.

  1. Module top level in network-interceptor/index.ts — defines _buf, _ready, _origin, and a message listener. On the first IS_NET_READY it sets _ready = true and posts every buffered event in order via _buf.splice(0).
  2. Guard if (!window.__isNetActive) — prevents wrapping twice if the script is injected again.
  3. isFetch(input, init). Calls getInitiator(). Normalises url, method, reqHeaders (headersToRecord), reqBody (bodyToStr(init?.body)). Posts req. Awaits the original fetch. Reads resp.clone().text(), capped at MAX_BODY, then posts res and returns the original resp. On a thrown error it posts err and re-throws, so page behaviour on failure is unchanged.
  4. ISXHR (subclass of the original XMLHttpRequest). open records method and URL. setRequestHeader records lower-cased headers. send(body) assigns a new id, start time and initiator, posts req, adds listeners for load (parses getAllResponseHeaders(), reads responseText when it is a string, posts res) and for error, abort, timeout (posts err with a fixed message), then calls super.send.
  5. getInitiator() — creates new Error().stack, skips frames containing chrome-extension://, matches at fn (url:line:col) or at url:line:col, returns lastPathSegment:line.
  6. post(data) — window.postMessage(data, _origin) if ready, else _buf.push(data).
  7. useNetworkMessages() in the content script — one window listener, re-created when isRecording changes. Drops the event if !isRecording or !isNetworkEvent(data). isNetworkEvent checks type === IS_NETWORK, event in req/res/err, and id is a string. Then req → addNetworkRequest({ ..., pending: true }); res → updateNetworkRequest(id, { status, ..., pending: false }); err → updateNetworkRequest(id, { error, duration, pending: false }).

5.4 Session restore (App.tsx)

  1. First useEffect — reads sessionStorage['is_session_v1']. If isVisible it calls setVisible(true). Replays each saved request through addNetworkRequest. Corrupt JSON is ignored.
  2. Posts IS_NET_READY so the interceptor flushes _buf.
  3. Registers handleUnload on beforeunload. It saves isVisible and the last 200 non-pending requests mapped through stripBodies (drops both bodies to stay inside the ~5 MB sessionStorage quota).

5.5 Export

  1. buildReport(reqs) — sorts by timestamp, emits { qcVersion: '1.0', exportedAt, pageUrl, userAgent, requestCount, requests[] }. Each entry has seq, request and response headers and bodies, and curl: toCurl(req).
  2. buildHar(reqs) — HAR 1.2 log.entries[] with startedDateTime, time, request (headers, queryString from getQueryString, postData with getMimeType), response (content.text), timings.wait = duration. Adds non-standard _initiator and _error.
  3. toCurl(req) — curl -X METHOD 'url', one -H per header, --data-raw for the body.
  4. triggerDownload(content, filename, mimeType) — Blob, object URL, synthetic click, revoke.

5.6 History navigation (useExecutionHistory.ts)

The small problem being solved. In a terminal, ArrowUp recalls the previous command. In a multi-line code editor, ArrowUp means "move the cursor up a line". Both behaviours are wanted, so the key is overloaded by position: ArrowUp recalls history only when the cursor is already on the first line and has nowhere further up to go, and ArrowDown only on the last line. The draft-saving in step 2 is the other half of the expectation — whatever you had half-typed comes back when you walk forward past the newest entry.

  1. historyExtension — a CodeMirror keymap. ArrowUp acts only when the cursor is on line 1; ArrowDown only on the last line. Otherwise the key moves the cursor normally.
  2. navigate(dir) — reads execHistory via getState(). Saves the current editor text as a draft on first leave (indexRef === -1). Sets skipNextChangeRef so the resulting onChange is not treated as a manual edit.
  3. handleChange(value) — on a real edit, resets indexRef to -1 and writes editorCode.

6.3 Edge case — the rewrite changes semantics and loses logs

Two separate bugs in four lines of user code. First: rewriting let i to var i changes what the program means. With let, each loop iteration gets its own i, so the three timers print 0, 1, 2; with var there is one i shared by all three, and by the time the timers fire it is already 3. The user wrote correct code and InSpectra silently ran different code. Second: the timers fire after the run is declared finished, and finish has already restored the real console.log — so their output goes to Chrome's DevTools console and never appears in the panel. Both are consequences of "run some code, decide it is done, clean up" being the wrong model for code that schedules work for later.

User code:

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i), 0)
  1. replCode = "for (var i = 0; ...". needsAsync = false.
  2. Eval runs the loop and schedules 3 timers. The last expression value is the third timer id, e.g. 187.
  3. 187 is not thenable → finish runs right away → console restored.
  4. The timers fire after finish. They call the page's real console.log, so nothing reaches the panel. With var they would print 3, 3, 3, not 0, 1, 2 — there is one shared i instead of one binding per iteration.
  5. Panel shows ← 187. i is added to __qcReplVars (value 3).

State after: outputs [..., return '187'], replVarCount +1, three logs visible only in Chrome DevTools.

Thrown error. Code loadWidgets() where no such function exists.

6.5 Network — buffer at load, then pause while in flight

What to watch for. Steps 1 to 5 are the buffer earning its keep: four requests' worth of events happen before the panel's React code exists, and none are lost. 9. Security model

The one thing to understand. The page is the attacker. Not because any particular page is hostile, but because InSpectra runs on every site and the page always controls its own JavaScript universe — where the interceptor and pageExecutor live. So everything arriving from the page is treated as untrusted data to display, never as instructions; results are addressed to one specific origin so a cross-origin iframe cannot read them; and incoming messages are shape-checked before they reach the store. One gap remains: the listeners check what a message looks like, not who sent it.

  • Trust boundary. The page is untrusted. The user explicitly runs code in it, so results returned from the page are data for display only.
  • Result confidentiality. Results and network events are posted only to the page's own origin (F3), so cross-origin iframes cannot read them.
  • Input validation. Network events pass a shape check (isNetworkEvent) before reaching the store (F4).
  • No outbound traffic. The extension makes no network requests of its own and has no backend.
  • Permissions. storage, activeTab, scripting, and all http(s) hosts. Required for page-context execution and interception on any site.

10. Build and run

Why a custom build.js instead of plain Vite. MV3 needs three separate self-contained bundles, not one app: the service worker, the content script and the interceptor each load independently and cannot share imports. So the build runs Vite three times in library/IIFE mode, then copies the manifest and icons and processes the Tailwind CSS. The ASCII-escaping step is a Chrome quirk — its content-script loader is happier with pure-ASCII files, so non-ASCII characters are rewritten as escape sequences.
